### Local changes

`tools/patches.py` holds every change as text replacements that `shared/tools/local_patches.py` applies to a fresh copy and checks (`--check`: undoing and redoing them must give back the tree byte for byte).

- **`kairo9x-*` groups:** the changes made to 86Box in the Kairo9X proof of concept, where this core began (KairoX86#183). They are the headless Android build (`src/unix/headless_main.c`, an SDL stub header, null audio, a SLiRP stub, the build files) and the exact speed fixes logged in [the core's speed record](core-performance.md) (the S3 FIFO fix, the ARM64 recompiler's block linking, timers, memory stubs, OPL synthesis and Sound Blaster mixing on their own threads, 8bpp line drawing on a second thread). Each fix reproduces the reference guest state bit for bit. They were taken from the Kairo9X working tree, and applying them to this snapshot gives back that tree's 49 changed and added files exactly.
- **`kairox86-license` group:** 86Box's cassette port (`src/device/cassette.c`, `src/include/86box/cassette.h`, from PCE) is GPL-2.0-only, which cannot ship beside the GPL-3.0-only shader runtime. Those files are removed and replaced by KairoX86's own `src/device/kairo_cassette.c` and `src/include/86box/kairo_cassette.h` (GPL-2.0-or-later), with the same calls and settings, written from the IBM cassette interface (a 1 bit is one 1 ms cycle, a 0 bit one 0.5 ms cycle) rather than from PCE's code. Every file that included the old header includes the new one. `src/network/net_vde.c` (VDE networking for Linux hosts, "GPL version 2") is removed and its build is switched off.
- **`kairox86-library` group:** KairoX86's build of the core (`core/CMakeLists.txt`). 86Box builds as a library (`KAIRO_LIBRARY`) that the machine loads afresh for each run, with KairoX86's frontend (`core/kairo/frontend.c`, `KAIRO_FRONTEND`) in place of the headless program and its null audio, and with the shared frontend's libchdr (`KAIRO_LIBCHDR`) in place of its bundled copy. libsndfile is taken through an interface target, and the CD image reader links it for its header. The version header names 86Box's own project (`PROJECT_*`), not the top-level one. The recompiler's pool goes in the nearest free place before or after the library, within 4 GiB, instead of one fixed address after the program. For Android 8 (API 26), which the app runs on: the PowerVR card's host clock uses `clock_gettime` instead of `timespec_get` (API 29), and `plat_run_command` (the serial port's host-command mode, `posix_spawn` from API 28) reports that it cannot run a host program, as an Android app cannot.
- **`kairox86-stop` group:** each CPU core's HLT that stays halted notes where it halted (`CPU_NOTE_HALT`, `cpu_halt_cs`/`cpu_halt_pc` in `src/cpu/386_common.c`): the 386 cores (`x86_ops_misc.h`), the 8088/8086 (`808x.c`), its cycle-exact core (`808x_marty_86box.c`) and the NEC V20/V30 (`vx0.c`). The frontend reads it with the flags to tell a processor stopped with interrupts off, so the machine ends with that reason (KairoX86#34). It changes no emulated state.
- **`kairox86-repeatable` group:** the SN76489 (the PCjr's and Tandy's sound) took its noise counters' start values from the C library's random numbers after seeding them from the host's clock, which also undid a repeatable run's seed for every other `rand()`. It takes them from 86Box's own random numbers (`random_generate`), seeded in a repeatable run and as random as before otherwise (KairoX86#36).
- **`kairox86-sync-render` group:** with `KAIROX86_SYNC_RENDER` defined (test builds only), every 8bpp line is drawn in place, to compare the threaded renderer against (KairoX86#38).
- **`kairox86-raster` group:** the threaded 8bpp renderer (`kairo9x-video`) drew a queued line later from VRAM and the live palette, so palette changes and VRAM written after the line was scanned showed in it, unlike drawing in place. A queued line now holds its VRAM bytes and the palette as the guest scanned it (KairoX86#38).
- **`kairox86-own-memory` group:** the platform files' `plat_mmap` and `plat_munmap` become `plat_mmap_os` and `plat_munmap_os`; the frontend's own record each mapping, and a machine's close unmaps what 86Box left (the recompiler's pool and tables). The library's `malloc` family goes through the frontend's record by the linker's `--wrap` (`core/CMakeLists.txt`), and the close frees what is left, so a closed machine gives back what it took (KairoX86#186).
- **`kairox86-halt-skip` group:** a halted 8088 (HLT repeating, nothing to interrupt it) ran one cycle at a time, though such a cycle only counts down a cycle, turns the bus interface's cycle and moves `tsc` on. `halt_skip` takes every cycle before the one where the next timer is due at once, since only a timer can end the halt; that cycle and the slice's last still run one at a time, and a memory refresh to do, a fetching queue, a held 80C88 clock or the newer bus interface take every cycle as before. Frame and sound hashes are unchanged; on the RG DS the XT's loading frames went from 42 to 79 frames/s with the two groups below (KairoX86#199).
- **`kairox86-halt-skip-vx0` group:** the same for the NEC V20/V30 core (`vx0.c`): a halted pass (`execute_instruction`'s cycle when no ModR/M is loaded and HLT's three) with the bus interface idle or suspended, no DMA cycle and no wait states only counts down, so `biu_halt_skip` takes every pass before the one where the next timer is due at once. Frame and sound hashes are unchanged; on the RG DS a V20 XT went from 47 to 66 frames/s over 3000 frames (KairoX86#205).
- **`kairox86-densel-once` group:** `fdd_type_invert_densel` searched the machine's name for "PS/1", "PS/2" and "PS/55" on every floppy bit; the answer is worked out once for each machine. Frame and sound hashes are unchanged (KairoX86#206).
- **`kairox86-lazy-pit` group:** the classic 8253/8254 (`pit.c` without `NEW_PIT`) ran its timer every half clock, about 2.4 million calls a second, though between the edges where a counter's output or state changes its edges only count down. `pit_schedule` sends the timer straight to the first falling edge any counter does more on, and the edges in between are counted down at once, there or as far as `tsc` has gone (`pit_catch_up`) before a port read or write, a gate, clock, `using_timer`, speed or reset change. 86Box runs every timer whose time is at or before `tsc` as `tsc` moves, so the edges counted are the ones it would have run by then. Frame and sound hashes are unchanged on the XT, an AT and a 386SX (KairoX86#199).
- **`kairox86-video-hoist` group:** 86Box builds without strict aliasing, so `video_process_8_monitor` and `cga_render` read their line (and the palette) again after every pixel's store; they read them once. Frame hashes are unchanged (KairoX86#199).
- **`kairox86-pages-as-reset` group:** a 386's page table covers the whole 4 GB address space (1,048,576 entries); `mem_reset` fills it and the CPU reset's `mem_reset_page_blocks` filled it again with the same values. `mem_pages_as_reset` records that the table is as `mem_reset_page_blocks` leaves it, and every other writer of its handlers or blocks (the memory remaps, the PS/2 MCA's, the recompiler taking a block) clears it, so the second pass is skipped only when it would change nothing. Frame and sound hashes are unchanged (KairoX86#200).
- **`kairox86-lazy-blocks` group:** the recompiler built its free list by adding all 32,768 blocks, each touching its entry and its link slots, at start and again at the CPU's reset, though most blocks are never used. Blocks not yet handed out since the list was built are now handed out as taken, in the order the list gave them and with the link generation adding them gave them, and a reset clears only the blocks ever used. Frame and sound hashes are unchanged; on the RG DS a start's `pc_init_modules` fell from 130-170 ms to 24-38 ms (KairoX86#200).
- **`kairox86-mouse-enable` group:** the PS/2 mouse (its enable, disable and reset commands), the serial mouse (RTS raised) and the bus mice (their interrupt enables) tell the frontend's `kairo_observe_mouse_enable` when the guest turns their reports on or off. With Windows's start and exit broadcasts (INT 2Fh AX=1605h/1606h), the frontend tells a protected-mode system driving the mouse from a DOS driver, for the Auto touch mode (KairoX86#190).
- **`kairox86-path-append` group:** `path_append_filename` copies its first part only when it is not already the destination: `add_path` appends a relative ROM folder in place, a copy onto itself that C leaves undefined (KairoX86#192).
- **`kairox86-native-size` group:** each frame, the VGA family (`svga_doblit`: the renderers that draw each pixel twice across, when no cursor, overlay or accelerator draws over them and the same renderer drew the whole frame) and the CGA (40-column text and 320-wide graphics, not composite; its line doubling) say on their monitor how many times they drew each pixel across and each line down, and the frontend keeps one of each, so the core hands the host the machine's own pixels (KairoX86#37).
- **`kairox86-guest-input` group:** every processor's INT decoder (the 386 and later interpreters, which the recompiler runs INT through, the 8088, the cycle-exact 8088 and the NEC V20/V30) passes each INT n, with AX and the caller's code address, to the frontend's `kairo_observe_int`, through the call's registers: it counts the BIOS keyboard waits and polls (INT 16h) and the mouse driver's reads (INT 33h) for the Auto touch mode (KairoX86#43), and for direct touch turns the program's next "get the position" (INT 33h AX=03h) into the driver's "set the position" (AX=04h) to the tapped point (KairoX86#44); with DS, it follows the console line DOS writes, so a keyboard read at a DOS prompt counts as the command shell waiting for a command (KairoX86#46).
- **`kairox86-pcem-430vx` group:** PCem's Award 430VX PCI, the board eXo's Windows 95 image (`Win95DX8.vhd`) was installed on (KairoX86#224). 86Box's `430vx` is that board (its BIOS, Super I/O and slots) but with a PIIX3 where PCem had the original PIIX, so Windows found new chipset functions and stopped to install them. `pcem_piix = 1` in 86box.cfg's `[KairoX86]` section (`config_kairo_int`) builds the board with the original PIIX; only the machines KairoX86 makes for an eXoWin9x DOSBox-X game whose Windows knows that board set it.
- **`kairox86-pci-dev0-card` group:** DOSBox-X's PCI bus has no host bridge, so its first card answers device 0. eXo's Windows 95 image (`Win95DX8.vhd`) met its Voodoo Graphics there, and its Glide is that card's (KairoX86#228). `pci_add_card_dev0()` puts a card at device 0 of bus 0 for registers 00h-4Fh of function 0, before the northbridge, which keeps the rest (the 430VX only stores values below 50h; the BIOS programs it above). `voodoo_pci_dev0 = 1` in 86box.cfg's `[KairoX86]` section puts the Voodoo there; only the machines KairoX86 makes for an image whose Glide is built for a Voodoo it met there set it.
- **`kairox86-gpu-scanout` group:** the scanout on the GPU (KairoX86#232, #233). With the machine's Hardware acceleration on (`[KairoX86] hardware_acceleration = 1`, `86box/kairo_gpu.h`, an added file), a bitmap's pixels live in memory the GPU shares, and the lines the renderers would draw are queued for the GPU (`core/kairo/gpu_scanout.c`) as the guest scans them, with what they read: the packed 8bpp lines KairoX86#38 queues for its drawing thread, the 15, 16 and 32bpp lines left of `hdisp` (15 and 16 bits only through 86Box's own colour tables) the low-resolution 15, 16 and 32bpp lines, the 24bpp lines, the mixed 15bpp lines, the 8bpp clone and Tseng lines, the general indexed path's character clocks (the VGA's planar 16-colour modes and its unchained 256-colour ones) and the text lines. A frame handed over (`video_blit_memtoscreen`), the SVGA drain points and a bitmap's end draw them all with one kernel (`core/kairo/shaders/scanout.comp`), so the frame is the one the CPU draws; a line out of the queue's order, and the CPU drawing on a queued line (`kairo_gpu_scan_touch`), draw the queue first. A line goes to the GPU only where the installed renderer is the core's own: a card's renderer around it (the Rage 128's pixel doubler) may read or redraw the line at once. Off, nothing changes.
- **`kairox86-gpu-cga` group:** the IBM CGA's display (and its clones', through `cga_poll`) on #233's scanout queue (KairoX86#241): `cga_render_gpu` takes each line's characters or pixel bytes as `cga_render` reads them, with the colours `video_process_8` gives them; the GPU's drain comes before `cga_interpolate` reads the picture, and the CPU's own drawing of a line (its borders, a blank line) draws any queued drawing of it first. Composite output and the light pen stay on the CPU.
- **`kairox86-whole-frames` group:** a frame handed over is copied whole (KairoX86#284). `video_blit_memtoscreen` only woke the blit thread, and the emulation ran on, drawing the next frame's first lines into the bitmap being copied; it now waits until the frontend has copied the picture (`video_wait_for_buffer`).
- **`kairox86-gpu-mda` group:** the IBM MDA's display on the scanout queue (KairoX86#263): `mda_render_gpu` resolves each character as `mda_poll` would draw it (RGBI or the attribute table, underline, the ninth column, the cursor's XOR) to the colour indexes `video_process_8` colours.
- **`kairox86-gpu-hercules` group:** the Hercules' display on the scanout queue (KairoX86#257): its text as the MDA's, its graphics at 1 bit a pixel; graphics with the blend option on stay on the CPU, and its borders and overscan bands draw a queued drawing of their rows first.
- **`kairox86-gpu-hercules-plus` group:** the Hercules Plus' display on the scanout queue (KairoX86#259): its text cells as `draw_char_rom`, `_ram4` and `_ram48` resolve them, its graphics at 1 bit a pixel; a line the CPU draws draws a queued drawing of its row first.
- **`kairox86-gpu-incolor` group:** the Hercules InColor's display on the scanout queue (KairoX86#258): its text cells as four planes' dots with the masks each dot's colour comes from (`draw_char_rom`, `_ram4`, `_ram48`: attributes, blink, bold, underline, strike-through, the cursor), its graphics as four planes, through the card's palette.
- **`kairox86-gpu-ega` group:** the EGA's display on the scanout queue (KairoX86#234, #251): `ega_render_text` and `ega_render_graphics` hand each line, read as they read it, to the queue (text cells; four graphics planes with odd/even addressing and the CGA 2bpp remap applied as read, the blink and plane mask folded into the palette). A line with the CRTC in reset stays on the CPU.
- **`kairox86-gpu-genius` group:** the Genius VHR's graphics on the scanout queue (KairoX86#255) when no text layer is drawn over them; its text layers, drawn over the pixels below, stay on the CPU.
- **`kairox86-gpu-wy700` group:** the Wyse 700's display on the scanout queue (KairoX86#279): text as pairs of 8-dot cells, graphics at 1 or 2 bits a pixel repeated 1, 2 or 4 times.
- **`kairox86-gpu-quadcolor` group:** the Quadram Quadcolor's display on the scanout queue with its second plane off (KairoX86#246); lines with the second plane on stay on the CPU.
- **`kairox86-gpu-v6355` group:** the Yamaha V6355D's display on the scanout queue (KairoX86#247); lines its mouse pointer crosses, and composite output, stay on the CPU.
- **`kairox86-gpu-svga-touch` group:** an SVGA line drawn again in a frame draws its queued GPU drawing first (`svga_do_render`), and the borders drawn over a line's ends after it (`scrollcache`) are cut out of the queued line (`kairo_gpu_scan_cut`).
- **`kairox86-gpu-pgc` group:** the IBM PGC's display and the ImageManager 1024's on the scanout queue (KairoX86#261, #268): native lines at 8 bits a pixel through the card's palette (the horizontal wrap applied as read), the CGA emulation's lines as text cells and 2 and 1-bit pixels.
- **`kairox86-voodoo-changed-pages` group:** on a Voodoo Banshee or Voodoo3, every 3D colour write (triangle spans, fast fills, LFB writes) marks the desktop's pages it lands on changed (`voodoo_mark_changed`), so the 2D display redraws them (KairoX86#287).
- **`kairox86-gpu-voodoo` group:** the 3dfx cards' triangles on the GPU (KairoX86#277, #278; `86box/kairo_gpu_voodoo.h`, an added file, and `core/kairo/gpu_voodoo.c`). With Hardware acceleration on, video memory (`svga_init`'s), the Voodoo Graphics/Voodoo2 frame buffer and every card's texture caches are memory the GPU shares (`kairo_gpu_alloc`); `voodoo_queue_triangle` records each triangle instead of handing it to the render threads, and `voodoo_wait_for_render_thread_idle` draws the recorded ones with one kernel (`core/kairo/shaders/voodoo.comp`, 86Box's C rasteriser in closed form). Where the processor reads or writes card memory without that wait (the Banshee's linear aperture and 2D engine, the 3D LFB's reads, texture downloads and decodes, the displays) it touches the memory first, which draws the recorded triangles if they draw there; the counter registers draw them all first, and the Banshee's display settle leaves the render wait to the touch. Off, nothing changes.
- **`kairox86-voodoo-stipple` group:** the rotating stipple as DOSBox-X has it (KairoX86#288): the register turns left, unsigned, once a pixel in raster order and keeps its place from triangle to triangle (`voodoo_triangle_pixels` at the queue, each line's start from the lines before it); both recompilers turn it left.
- **`kairox86-voodoo-depth-source` group:** `DEPTH_TEST` parenthesises its argument, so the depth source zaColor is compared against the depth buffer (KairoX86#290).
- **`kairox86-voodoo-display-settle` group:** the Voodoo Graphics/Voodoo2 display settles the card before it reads a line, as the Banshee's does (KairoX86#291).
- **`kairox86-gpu-scanout-rest` group:** the remaining core renderers on the scanout queue (KairoX86#233): the S3's 2bpp lines (one loop for both address forms) and the Headland's 2bpp and Tseng's 4bpp lines (their 8-pixel groups' nibbles) as bit lines, and the ATI 28800's KSC5601 text as text cells; each loop draws its pixels or gathers what the GPU line needs.
- **`kairox86-virge-clip-and-settle` group:** a ViRGE triangle half starting below the hard clip rectangle moves its rows with the lines it skips (KairoX86#292); before each line the ViRGE waits for its FIFO and its 3D engine, so the picture follows what the guest queued, not the host's threads (KairoX86#293).
- **`kairox86-gpu-virge` group:** the S3 ViRGE's triangles on the GPU (KairoX86#272; `86box/kairo_gpu_virge.h`, an added file, `core/kairo/gpu_virge.c`, `core/kairo/shaders/virge.comp`). With Hardware acceleration on, `queue_triangle` records each triangle (with the changed-page marks `tri()` makes) instead of handing it to the render threads, and the wait for the 3D engine draws the batch. The SVGA core gets a touch hook (`svga->kairo_touch`) its memory handlers call before they read or write video memory; the ViRGE draws its batch there where it draws on them, at its 2D engine's start and at each line the display shows.
- **`kairox86-gpu-display-touch` group:** the display's GPU touches, shared by every card with GPU work in its video memory (KairoX86#237): before a line is drawn, `svga->kairo_touch` on its memory; before the overlay, on all of it; before either cursor, on a whole cursor's memory. The ViRGE's own line touch goes.
- **`kairox86-gpu-mach64` group:** the ATI 3D Rage II+'s 3D engine and front-end scaler on the GPU (KairoX86#237; `86box/kairo_gpu_mach64.h`, an added file, `core/kairo/gpu_mach64.c`, `core/kairo/shaders/mach64.comp`). With Hardware acceleration on, `mach64_3d_draw_rows` records the rows a trapezoid or a 3D line has walked, with what their pixels read, and marks the pages they may write changed; the scaler records its destination lines. The GPU draws them where the processor (the linear aperture, the SVGA core), the display, the 2D engine (each operation's start, its host data, the context load) meets their memory. A 3D line's pixels become rows of one, drawn by `mach64_3d_draw_row` as a trapezoid's are; the scaler is split into its setup and a pixel.
- **`kairox86-powervr-render-timing` group:** the PowerVR PCX2's end of render comes at the frame's emulated render time; a frame the host has not finished is waited for there instead of holding the end of render back in emulated time, so the guest sees the same moment in every run (KairoX86#294).
- **`kairox86-gpu-powervr` group:** the PowerVR PCX2's tiles on the GPU (KairoX86#269; `86box/kairo_gpu_powervr.h`, an added file, `core/kairo/gpu_powervr.c`, `core/kairo/shaders/powervr.comp`). With Hardware acceleration on, its texture memory and RGB buffer are GPU-shared, and the render thread hands `pcxr_gpu_lists`' lists (decoded planes and objects, each span with its decoder schedule) to the kernel instead of drawing the tiles itself.
- **`kairox86-mach64-display-settle` group:** a Mach64 line is drawn once the 2D engine's FIFO has run out (`svga->render_sync`, `mach64_wait_fifo_idle`), so the picture does not follow the host's thread (KairoX86#295), as the ViRGE's and the Voodoos' displays settle.
- **`kairox86-gpu-mach64-2d` group:** the Mach64 2D engine on the GPU (KairoX86#237), every Mach64 from the GX on, on the drawing engines' shared batches (`86box/kairo_gpu_seg.h`, an added file, `core/kairo/gpu_seg.c`, `core/kairo/shaders/seg.glsl`; the card's `core/kairo/gpu_mach64_2d.c`, `core/kairo/shaders/mach64_2d.comp`). The rectangle's and the line's draw and step are split (`mach64_rect_draw`/`_advance`, `mach64_line_draws`/`_draw`/`_advance`); with Hardware acceleration on, an operation's record and rows go into the batch where it starts, or as the host feeds them, and the engine's walk stays the CPU's. Each recorded row marks the display's changed pages as the CPU's writes do. The batch is drawn first where the processor, the display, the 3D engine or a later operation meets its memory: a later operation that reads what the batch draws, or draws what it reads.
- **`kairox86-p9100-outline` group:** the Weitek Power 9100's oversized quad outline (`p9100_quad_outline`) steps as Bresenham does, both tests taking the error as the step began (KairoX86#296). Testing the updated error let the walk miss its end point, and the machine hung in the quad command.
- **`kairox86-gpu-p9100` group:** the Weitek Power 9100's drawing engines on the GPU (KairoX86#266; `86box/kairo_gpu_p9100.h`, an added file, `core/kairo/gpu_p9100.c`, `core/kairo/shaders/p9100.comp`), on the drawing engines' shared batches. With Hardware acceleration on, the native engine's quads, blits, pixel1 and pixel8 runs, and the W5286 GHA's blits and lines, are recorded where they run: native rows as runs of bytes, so every pixel size runs in parallel, and GHA rows as runs of longwords. The batch is drawn first where the frame buffer, the SVGA core, the display or the GHA's instruction queue meets it.
- **`kairox86-gpu-et4000w32` group:** the Tseng Labs ET4000/W32, W32i and W32p accelerator on the GPU (KairoX86#254; `86box/kairo_gpu_et4000w32.h`, an added file, `core/kairo/gpu_et4000w32.c`, `core/kairo/shaders/et4000w32.comp`), on the drawing engines' shared batches. The five walks' per-byte draw (`et4000w32_blit`, `et4000w32p_blit`, their lines) is one helper, `et4000w32_draw_byte`. With Hardware acceleration on it records each run of destination bytes the walk draws (the shared byte runs, `core/kairo/gpu_seg_run.c`), with every byte's pattern address, source (the host's byte or an address) and mix (the host's bit or the mix map's). A run is drawn in order where it reads what it draws, and the batch first where a run reads what it draws or draws what it reads. A result routed to the processor (ctrl_routing 40h) is drawn on the CPU after the batch. The walk stays the CPU's.
- **`kairox86-gpu-cl54xx` group:** the Cirrus Logic GD54xx BitBLT engine on the GPU (KairoX86#250; `86box/kairo_gpu_cl54xx.h`, an added file, `core/kairo/gpu_cl54xx.c`, `core/kairo/shaders/cl54xx.comp`), on the drawing engines' shared batches as runs of bytes (`core/kairo/gpu_seg_run.c`). The pattern copy's, the system memory source's and the normal blit's per-byte draw goes through one helper, `gd54xx_draw_byte`, with descriptors for each byte's source (the host's byte, a byte of video memory, or a colour-expansion bit in it), its mask (known, the expansion bit, or a transparent comparison) and the skip. In software they are read as the original read them; with Hardware acceleration on they are recorded and the GPU reads them. Each blit's run goes in when the blit's walk ends. The system memory destination's buffer fill and the 5480's command list touch the batch. The walk stays the CPU's.
- **`kairox86-gpu-chips69000` group:** the Chips & Technologies B69000 BitBLT engine on the GPU (KairoX86#249; `86box/kairo_gpu_chips69000.h`, an added file, `core/kairo/gpu_chips69000.c`, `core/kairo/shaders/chips69000.comp`), on the drawing engines' shared batches as runs of pixels of 1 to 3 bytes (`core/kairo/gpu_seg_run.c`). The runs go in order where their pixels can cross a word. With Hardware acceleration on, `chips_69000_process_pixel` records each pixel's source (the pixel, or the address of a pixel in video memory the copy loop no longer reads) and pattern (the pixel, a mono pattern bit's address, or a colour pattern's). Raster operation, colour keying and the mono pattern's write mask go in the operation's record. A pixel with an address in the MMIO window is drawn by the processor after the batch. The software path is unchanged; the walk stays the CPU's. Each guest access to the engine's registers or data port puts its runs in.
- **`kairox86-gpu-tgui` group:** the Trident TGUI graphics engine on the GPU (KairoX86#274; `86box/kairo_gpu_tgui.h`, an added file, `core/kairo/gpu_tgui.c`, `core/kairo/shaders/tgui.comp`), on the drawing engines' shared batches as runs of 1, 2 and 4-byte pixels. Every draw of `tgui_accel_command` goes through one helper, `tgui_draw_pixel`: blits from the host or the screen, scanlines, Bresenham lines, short vectors and fast lines. With Hardware acceleration on it records each pixel's source (the value, or the address of a screen pixel, with its transparency check) and pattern. The extended write modes and the copy latches touch the batch. The walk stays the CPU's.
- **`kairox86-gpu-xga` group:** the IBM XGA's drawing engine on the GPU (KairoX86#280; `86box/kairo_gpu_xga.h`, an added file, `core/kairo/gpu_xga.c`, `core/kairo/shaders/xga.comp`), on the drawing engines' shared batches as runs of 1 and 2-byte pixels. With Hardware acceleration on, the XGA's own memory is memory the GPU shares. Each pixel of the engine's twelve draw blocks (BitBLT, area fill, line draw, short strokes) goes to the GPU through `xga_k_pixel`: the colour compare, the mix (the arithmetic ones too) and the plane mask, in 1, 2, 4, 8 and 16-bit maps. The source and the mix are read by the walk, which stays the CPU's. A destination map in system memory is the processor's, after the batch. The maps' and the processor's accesses, and the display's lines, touch the batch. The software blocks are unchanged.
